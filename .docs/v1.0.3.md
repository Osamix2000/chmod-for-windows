# v1.0.3 ディレクトリACL設計・回帰修正

> 実装・検証基準日: 2026-10-16  
> 対象version: `chmod-for-windows v1.0.3`  
> 主検証環境: Windows Server 2025 / build 26100 / NTFS

## 1. この文書の目的

v1.0.3では、v1.0.1で導入したfile/directory ACL分離の制御フロー回帰を修正すると同時に、directoryのMODEと子要素へ継承されるWindows ACLを分離した。

この文書は、その設計理由、実装上の不変条件、Windows Server 2025で確認した結果、未検証範囲を記録する。

GNU/POSIXの一般仕様は[`chmod.md`](chmod.md)、Windows ACL / `icacls`の一般仕様は[`icacls.md`](icacls.md)を参照する。

---

## 2. v1.0.1以降の制御フロー回帰

v1.0.1ではfileとdirectoryのACL処理を分離する変更を行ったが、実装上は次の回帰が残っていた。

- `:apply_current`からfile時に`call :apply_file_acl`するよう変更された
- 一方で`:apply_file_acl`ラベルが実際には追加されていなかった
- directory ACL適用後もreport/returnせず、旧file ACL処理本体へfall-throughし得る構造になっていた

その結果、directory用に構築したACLが後段のfile用処理で再構成され、意図したACLが失われる場合があった。

v1.0.3では:

1. `:apply_file_acl`ラベルを明示的に復元
2. directory/fileの各handlerから適用後にreport/returnする制御フローを復元
3. directory処理後にfile処理へfall-throughしない

よう修正した。

この問題はWindows ACL APIそのものではなく、本プロジェクト側のbatch制御フロー回帰だった。

---

## 3. directory MODEと子ACLを分離する理由

GNU/POSIXのdirectory MODEは、そのdirectory自身に対するread/write/search permissionを表す。

`chmod 700 dir`を行ったからといって、将来`dir`の中で新規作成されるfileが自動的に`700`相当になるわけではない。新規子のmodeは作成要求やumask等の別要因で決まる。

一方Windowsでは、directoryのACEへ`(OI)(CI)`を付けると、そのACEは子file / child directoryへ継承可能になる。

v1.0.1の「directoryのu/g/o MODE ACEへそのまま`(OI)(CI)`を付ける」設計は、対象directory自身のMODE近似と将来子のdefault ACLを同じACEで兼用していた。

これはWindowsでは自然に見える一方、GNU `chmod DIR`の意味とは異なり、例えば`chmod 700 DIR`後に新規作成した一般的なWindows fileまでCurrent User中心の制限ACLへ寄せる原因になり得る。

v1.0.3ではこの2役を分離する。

---

## 4. v1.0.3のdirectory DACL構成

数値`777`以外のdirectory MODEでは、概念的にDACLを次の2層として構成する。

### 4.1 対象directory自身へ有効なACE

対象directory自身には次を置く。

- `SYSTEM`: Full Control
- `Administrators`: Full Control
- `u`: 指定MODEに対応するCurrent User権限
- `g`: 指定MODEに対応する`BUILTIN\\Users`権限
- `o`: 指定MODEに対応する`Everyone`権限

これらのu/g/o MODE ACEには、将来子へMODEそのものを伝播させるための`ObjectInherit` / `ContainerInherit`を付けない。

SYSTEM / AdministratorsのFull Control維持はGNU互換ではなく、Windows上の管理・復旧経路を失いにくくする本プロジェクト安全方針である。

### 4.2 将来子用のInheritOnlyテンプレート

対象directoryの親DACLから、子へ継承可能なACEを取り出し、対象directory上では効かない`InheritOnly` ACEとして保持する。

概念:

```text
親directoryの inheritable ACE
        ↓
OI / CI等を保持
Inherited flagは除去
InheritOnlyを付加
        ↓
chmod対象directory自身には非適用
        ↓
将来作成される子へWindows通常継承として利用
```

これにより:

- `chmod 700 DIR`の`700`近似はDIR自身へ効く
- DIRの親が持つWindows標準ACLや独自の継承可能ACEは、将来子用templateとして残る
- 親由来template ACEは`InheritOnly`なので、DIR自身の制限MODEを不用意に広げない

`NoPropagateInherit`付きACEは、その意味を単純に1階層ずらして複製すると本来の伝播範囲を変える可能性があるため、v1.0.3ではtemplate化対象から除外する。

---

## 5. 既存Explicit ACEの扱い

対象directoryにもともと存在するExplicit ACEのうち、本プロジェクトが管理する主要SID以外のACEは可能な範囲で保持する。

本プロジェクトがMODE再構成対象として扱う主要SID:

- Current User
- `BUILTIN\\Users`
- `Everyone`
- `Authenticated Users`
- `Administrators`
- `SYSTEM`

これらについてはMODE近似とWindows安全ACEを再構成する。

一方、独自アプリケーションSID等のExplicit ACEを一律に消すことは避ける。

これは「POSIX modeへ完全正規化する」より、Windows上の既存Security Descriptor情報を必要以上に破壊しないことを優先した設計である。

## 6. 実装方式

### 6.1 `icacls`だけにしなかった理由

`icacls`は通常のgrant/remove/inheritance操作には適しているが、今回必要な:

- 対象directoryへ効くMODE ACE
- 対象directoryには効かず将来子へだけ伝わる親ACL template
- 既存Explicit ACEの選択的保持
- raw access mask / ACE flagsの維持

を1回の安全な再構成として扱うには制約が大きい。

特に`/inheritance:r`と`/grant`の組み合わせだけでは、親由来の継承可能ACEを「対象には非適用だが将来子には有効」という形へ一般的に写し替えるのが難しい。

### 6.2 Windows PowerShell 5.1 / .NET ACL API

v1.0.3では数値`777`以外のdirectory ACL適用時だけ、Windows標準搭載のWindows PowerShell 5.1を内部的に使用する。

利用する主な.NET型:

- `System.Security.AccessControl.RawSecurityDescriptor`
- `System.Security.AccessControl.RawAcl`
- `System.Security.AccessControl.CommonAce`

最終適用は`advapi32.dll`の`SetNamedSecurityInfoW`をP/Invokeし、DACLをProtected状態として設定する。

外部のPowerShell 7 / `pwsh`は不要で、`%SystemRoot%\\System32\\WindowsPowerShell\\v1.0\\powershell.exe`またはWOW64回避用`Sysnative`を使用する。

したがってv1.0.2までREADMEにあった「PowerShell不要」はv1.0.3のdirectory処理には当てはまらない。

### 6.3 ACE順序

再構成時は概ね:

1. Explicit Deny
2. Explicit Allow
3. その他保持ACE

のbucket順でRaw ACLへ挿入する。

Windows ACLのcanonical orderを壊さないことを優先する。

## 7. `777`の扱いは変更しない

v1.0.3でもdirectory numeric `777`は本プロジェクト独自のWindows復旧操作である。

```bat
chmod 777 DIR
```

はGNUのliteral `u=rwx,g=rwx,o=rwx`再現ではなく:

- ACL継承を有効化
- `icacls /reset`で親由来の通常Windows ACLへ戻す

操作として扱う。

```bat
chmod -R 777 DIR
```

ではsubtreeも同様に通常継承状態へ戻す。

---

## 8. 非再帰と再帰の意味

### 非再帰

```bat
chmod 700 DIR
```

ではDIR自身へMODEを適用する。

既存childへ`chmod`を明示実行するtree walkは行わない。

WindowsのACL自動継承機構によりSecurity Descriptorのcontrol metadataが再計算される場合はあるが、v1.0.3のWindows Server 2025検証では既存childのaccess rule signatureは維持された。

### 再帰

```bat
chmod -R 700 DIR
```

では既存subtreeを明示走査し、各対象へMODEを適用する。

ただし各directoryには将来子用の通常Windows inheritance templateも保持するため、`-R`後に新規作成されるchildへMODE ACEそのものをdefault ACLとして強制する設計ではない。

---

## 9. compound symbolic MODEと`cmd.exe`

Windowsのbatch/cmd引数解析では、`=`や`,`を含む複合symbolic MODEを未引用で渡すと、`chmod.bat`へ1つのMODE引数として届かない場合がある。

そのためv1.0.3では、次のようにMODE全体を引用することを正式な使用例とする。

```bat
chmod "u=rw,go=r" file
chmod "u=rw,go=" private.key
```

単純な:

```bat
chmod u+x file
chmod go-rwx file
chmod a+rX dir
```

は従来どおり引用なしで使用できる。

これはsymbolic parserのpermission意味論ではなく、Windows command-line / batch引数境界の制約である。

## 10. Windows Server 2025実機検証

GitHub ActionsのWindows Server 2025 / build 26100環境で、少なくとも次を確認した。

- directory `700`
- `SYSTEM` Full Control維持
- `Administrators` Full Control維持
- 非再帰directory変更後の既存child access rule維持
- MODE適用後に新規作成したchildが通常Windows ACLを持つこと
- 親directoryへ追加した独自inheritable `Everyone` ACEが、chmod対象自身のeffective accessへ漏れず、将来childへ継承されること
- file `600`
- `-v`
- `-c`
- `-R 700`
- `-R 777`
- symbolic `u+x`
- quoted compound symbolic MODE
- CP932 round-trip
- CRLF-only
- `--help`

既存childの比較ではSecurity Descriptor全体のSDDL完全一致ではなく、access rule signatureを主に比較した。

Windowsは自動継承処理で`SE_DACL_AUTO_INHERITED`等のcontrol metadataを更新し得るため、ACE意味が同じなのにcontrol flag差だけで失敗扱いしないためである。

## 13. 保守上の不変条件

v1.0.3のdirectory処理を変更する場合、最低限次を守る。

- directory処理後にfile ACL handlerへfall-throughさせない
- `:apply_file_acl`ラベルを失わない
- directory自身のMODE ACEとfuture-child inheritance templateを同一ACEへ戻さない
- parent inheritable ACEをtarget effective accessへ不用意に漏らさない
- SYSTEM / Administrators安全ACE方針を変更する場合は明示的な仕様変更として扱う
- `777`のWindows復旧意味をliteral POSIX 777へ黙って変更しない
- CP932 / CRLF / tab indentationを維持
- `chmod.bat` bytes変更時は`.update`を同一release単位で更新
- 前versionの実配布updaterから次versionへのE2Eを行う

この設計の目的は「Windows ACLをUnix mode bitsへ無理に変形すること」ではなく、**対象自身のGNU/POSIX的意図とWindowsの自然な子ACL継承を可能な範囲で分離し、安全に共存させること**である。
